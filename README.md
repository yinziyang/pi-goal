# pi-goal

为 pi 提供与 Claude Code 语义一致的 `/goal`。
设定一个完成条件后，agent 自动一轮接一轮地工作，每轮结束由一个独立的模型对照对话判断条件是否成立，直到达成为止。

## 用法

- `/goal <完成条件>`：设定目标，立即以条件本身为指令开始一轮。已有目标时被新目标替换。条件最长 4000 字符。
- `/goal`：查看状态。进行中时显示条件、已运行时长、已评估轮数、token 用量、最近一次评估理由。没有进行中的目标但本会话达成过时，显示达成的条件及其统计。
  - `/goal` 后面只跟 `status`、`show`、`progress`、`状态`、`进度`、`查看`、`查看进度`、`查看状态`、`进展`、`查看进展` 之一时，同样是查看状态，不会被当成新条件。
  - 这是相对 Claude Code 有意增加的一处：Claude Code 会把这类文字当成新条件，已有目标会被悄悄替换。
- `/goal clear`：清除目标。`stop`、`off`、`reset`、`none`、`cancel` 是它的别名。

非交互模式可以一次跑完整个循环：`pi -p "/goal CHANGELOG.md 为本周合并的每个 PR 都有一条记录"`。

## 状态显示

目标进行中时，输入框正下方右侧显示 `◎ /goal active · 3m 20s`，暂停时显示为警告色的 `◎ /goal paused · …`，位置与 Claude Code 一致。
目标结束后指示消失，对话里留一张结束卡片，写明结果、耗时、轮数、token 与评估理由。

这里用的是编辑器下方的小部件（`setWidget` 的 `belowEditor`），而不是：

- `setStatus`：内置底栏会把所有扩展的状态靠左拼成单独一行，没有右对齐的选项。
- `setFooter`：会替换整个内置底栏，token、成本、上下文占比都要自己重写，还会和其他改底栏的扩展互相覆盖。

RPC 模式不支持组件类的小部件，那里退回用 `setStatus` 发送同样的文本。

## 写好条件

评估者不运行命令、不读文件，只根据对话里已经出现的内容判断。
所以条件应当是 agent 自己的输出能够证明的事情，例如「`npm test` 退出码为 0」，而不是「代码质量很好」。

- 写清一个可度量的结束状态：测试结果、构建退出码、文件数量、清空的队列。
- 写清怎么证明：例如「`git status` 是干净的」。
- 写清途中不能变的约束：例如「不修改其他测试文件」。
- 要限制运行时长，就把它写进条件，例如「或者 20 轮后停止」。

## 评估与停止

每轮结束后，评估者给出三种判定之一：

- 未达成：把理由作为指引，自动开始下一轮。每次评估都会作为一条消息显示在对话里。
- 达成：清除目标，记一条达成记录。
- 不可能达成：清除目标，记一条失败记录及理由。

循环还会在以下情况停下：

- 连续 3 轮没有调用任何工具：暂停，目标保留，发送任意消息后恢复评估。
- 你中断了本轮：暂停，同上。
- 认证失败、额度耗尽、压缩后仍然上下文溢出、模型不可用：清除目标，修复后重新执行 `/goal`。
- 其他错误（限流、网络抖动、服务过载等）：先由 pi 的自动重试处理（`settings.json` 的 `retry`），重试仍失败则暂停。
- 评估请求失败：暂停，并显示失败原因。

恢复会话（`pi --session`、`/resume`）时，进行中的目标会被恢复，轮数、计时与 token 从零重新计。
已达成或已清除的目标不会被恢复。
`/new` 开始新会话时目标不会带过去。

## 评估模型

默认使用当前会话的模型。
用环境变量 `PI_GOAL_MODEL=<provider>/<modelId>` 可以换成别的模型，只影响 `/goal` 的评估。
配置的模型找不到时会提示并退回当前模型。
模型存在但服务端拒绝时（例如 ChatGPT 账号不支持的 Codex 模型），评估失败，目标暂停。

## 与其他扩展的配合

评估与续跑在 `agent_end` 进行，只为用户排队的消息让路，不为其他扩展排入的续跑消息让路。
与同样在 `agent_end` 续跑的扩展（例如 `pi-coding-standards` 的收尾检查）同时启用时，两边的续跑消息都会送达，与加载顺序无关。
两边是在同一时刻各自决定续跑的，所以目标的续跑消息反映的是收尾反馈处理之前的状态。
模型处理完收尾反馈后再看到它时，里面的「还差什么」可能已经过时，通常只会多一轮核实，下一次评估会按最新对话重新判断。

## 实现要点

- 评估放在 `agent_end` 而不是 `agent_settled`：`pi -p` 在 `agent_settled` 之后就拆掉会话，那时再续跑会失败。
- 出错的轮次留到 `agent_settled` 才判定，因为在 `agent_end` 时 pi 可能还会自动重试。
- 非交互模式下 `/goal` 命令会等待整个循环结束才返回，否则 pi 会在命令返回时截断刚开始的那一轮。
- 状态用会话条目保存，随分支走，`/tree` 切换分支后按那条分支还原。
- 条件与对话都作为数据包裹后交给评估者，防止其中的文字被当成指令。

## 与社区实现的区别

`pi-goal-x`、`@narumitw/pi-goal`、`pi-codex-goal` 都由干活的 agent 自己报告完成。
本包按 Claude Code 的设计，由独立的模型判断完成，不给评估者工具，不修改活跃工具集，不改写发给模型的请求，不在项目目录写文件。
借鉴了社区实现里验证过的做法：隐藏标记与目标 id 防止过期续跑、会话条目持久化、连续无工具调用判定为无进展、按错误类型区分清除与暂停。

## 开发

- `npm test` 运行全部测试，需要先 `npm install` 装上固定版本的 pi 作为开发依赖。
  - `test/state.test.ts`、`test/evaluator.test.ts` 是纯函数的单元测试。
  - `test/index.test.ts` 在真实的 pi 会话里加载本扩展，用 pi-ai 的 faux provider 按脚本回复，跑完整个 `/goal` 循环，覆盖事件时序。
  - 升级 pi 时先改 `devDependencies` 里的版本再跑测试。
- 源码在 `extensions/goal/`：`state.ts` 是命令解析、记录与状态还原，`evaluator.ts` 是评估输入的整理与判定解析，`index.ts` 是 pi 事件接线。
